# Feature Specification: 007 Web Console Refactoring and Modularization

**Feature Branch**: `007-web-console-refactor`

**Created**: 2026-11-22

**Status**: Draft

**Input**: User description: "web/index.htmlを解析していきたい。最終ゴールは、Codexが当該アプリの仕様を理解し、リファクタリングや改修を行えるようにしたい。"

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 仕様・プロトコルの完全理解と仕様書化 (Priority: P1)

AIエージェント（Codex等）や開発者が `web/index.html` の全機能、BLE通信プロトコル、データモデル（SEG, ACTION, ルールバイナリ構造）、状態遷移、UI構成を正確に理解でき、疑問なく設計・改修の判断を行える状態にする。

**Why this priority**:
単一ファイル内に約11,300行のコードが凝縮されており、仕様の正確なドキュメント化と構造把握なしにリファクタリングや機能追加を行うと、車体通信の不具合やデータ破損を引き起こすリスクがあるため最優先。

**Independent Test**:
- 作成された仕様ドキュメントおよびデータ契約をもとに、開発者/AIが各BLEキャラクタリスティックの役割とパケット形式、およびルール構造を即座に説明・検証できること。

**Acceptance Scenarios**:
1. **Given** `web/index.html` の既存実装、**When** 仕様書（アーキテクチャ・プロトコル定義）を参照した際、**Then** BLE UUID、コマンドバイト列、47バイト/ルールのエンコード仕様、バルクログ受信構造が漏れなく網羅されていること。
2. **Given** セグメント認識（`SEG`）および制御アクション（`ACTION`）、**When** ルール設定を行う際、**Then** 各パラメータの境界値（clamp範囲）とUI・通信間の変換ルールが明確であること。

---

### User Story 2 - バイナリプロトコル & ルール処理の独立モジュール化とテスト整備 (Priority: P2)

DOM操作やBLE通信から、ルールのエンコード/デコードロジック、パケット解析ロジック、自然文生成ロジックを純粋関数として分離し、ブラウザ外（Node.js / Vitest等）で単体テストが実行できるようにする。

**Why this priority**:
ミニ四駆実機との通信フォーマット破壊を防ぐ安全網（セーフティネット）を最優先で確立するため。

**Independent Test**:
- 実機やWeb Bluetoothなしで、ルール定義JSONをバイナリ（Uint8Array）に変換し、既存のファームウェア互換データと完全一致することを検証する単体テストがパスすること。

**Acceptance Scenarios**:
1. **Given** 任意のルールオブジェクト配列、**When** `encodeRules` 相当のモジュール関数を実行した際、**Then** 従来の `index.html` が出力するバイト列と1バイトの狂いもなく完全一致すること。
2. **Given** 車体から受信したバルクログのパケットバイト列、**When** パーサー関数を実行した際、**Then** タイムスタンプ、角速度、電圧、温度、発火ルールが期待通りのオブジェクト配列に復元されること。

---

### User Story 3 - 静的アセット・UI・ライブラリのディレクトリ分離 (Priority: P3)

単一ファイル（11,295行）からCSSスタイルシート、インライン外部ライブラリ（qrious, jsQR, lz-string）、およびUI各画面（ヘッダー、ワークスペース、ウィザード、モーダル）を論理的に分離し、保守性と変更容易性を向上させる。

**Why this priority**:
スタイルの変更や新機能追加の際に巨大な1ファイルを編集する必要をなくし、Codex等のLLMがコンテキストサイズ内に収まる単位で安全にコード修正を行えるようにするため。

**Independent Test**:
- 分離後の各ファイルを参照・ビルド（またはブラウザ直接読み込み）した際、元の単一 `index.html` と視覚的・機能的に同一の挙動を示すこと。

**Acceptance Scenarios**:
1. **Given** 分割後のWebコンソール、**When** ブラウザで開いた際、**Then** 従来のUIレイアウト、アニメーション、テーマ表示が崩れず動作すること。
2. **Given** 各種モーダル（ウィザード、QR、ヘルプ、保存確認）、**When** 開閉操作を行った際、**Then** 既存と同等のレスポンスと画面遷移が維持されること。

---

### Edge Cases

- **ファームウェア後方互換性**: ファームウェアバージョン（v3.44以前、v3.58、v4.x）によってバルクログのパケット長（20バイト〜28バイト）やラップトレーラーの有無が異なる。パーサーは可変長・旧形式パケットを安全に識別・フォールバックできる必要がある。
- **LocalStorage互換性**: 既存ユーザーがブラウザに保存しているルール設定キー（`mini4ai_rules_v4_16` 等）を破壊せず、シームレスに引き継げる必要がある。
- **GATT操作競合**: Web Bluetoothでは同一デバイスに対する並行GATTリクエストが禁止されているため、モジュール化後もキューイング機構が確実に排他制御を保証する必要がある。

---

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、Web Bluetooth GATTプロトコル（サービスUUID `...abcdef0`、キャラクタリスティック12種）の通信仕様を完全に定義・維持しなければならない。
- **FR-002**: システムは、ルール定義（最大8件、47バイト/ルール ＋ 16バイトラップトレーラー）のバイナリシリアライズ処理を独立モジュールとして提供しなければならない。
- **FR-003**: システムは、停止後バルクログのパケットパーサーおよび信頼性シーケンス要求（`reliableDump`）ロジックを分離・提供しなければならない。
- **FR-004**: システムは、ルールから自然文（「直線 を見たら、…」）を生成する表示ロジックをUIから独立して実行可能にしなければならない。
- **FR-005**: システムは、外部ライブラリ（`qrious`, `jsQR`, `lz-string`）をインライン直接埋め込みから標準的なモジュールインポートまたは別ファイル読み込みに分離しなければならない。
- **FR-006**: システムは、CSS（約3,200行）をテーマ変数、レイアウト、コンポーネント別に分離管理できるようにしなければならない。
- **FR-007**: システムは、モジュール分割後も既存のすべての機能（走行開始/停止、パラメータ調整、ルール編集、プレビューシミュレーション、ウィザード、QR共有）が退行（リグレッション）なく動作することを保証しなければならない。

### Key Entities *(include if feature involves data)*

- **Rule**: ミニ四駆の走行制御単位。`pattern`（セグメントID配列 1〜8）、`actions`（動作配列 1〜5）、`triggerMode`、`triggerN`、`priority`、各種タイミング値（`peakAfterMs`, `wildcardMs` 等）、`_guideMeta` を保持。
- **TelemetrySample**: リアルタイム走行データ。角速度、推定速度、電圧VBAT、電圧サグ、基板温度、現在セグメント。
- **BulkLogRow**: 走行停止後に車体Flashから受信した高密度ログ1行分。ミリ秒、セグメント、ルール番号、角速度、電圧、温度等。
- **WorkspaceConfig**: UIカードの表示状態、並び順、折りたたみ設定、テーマ（会場モード）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: `web/index.html` の仕様書（アーキテクチャ、データモデル、BLEプロトコル）が完成し、リポジトリ内に永続化されていること。
- **SC-002**: プロトコル変換・ルールエンコード処理が独立したテストスイートで検証可能になり、既存実装との100%バイト互換性が自動テストで実証されること。
- **SC-003**: 11,295行の単一ファイルが、責務ごとに分割されたファイル群（1ファイルあたり最大1,000行以内を推奨）へと整理され、Codex/LLMが単一ファイル単位でコンテキストを圧迫せずに編集できるようになること。
- **SC-004**: リファクタリング後も既存のブラウザ（Chrome/Edge）でWeb Bluetooth接続し、実機またはエミュレータと正常に対話できること。

---

## Assumptions

- ユーザー環境はWeb Bluetooth APIをサポートする最新のデスクトップ/モバイルブラウザ（Chrome, Edge等）を使用する。
- 車体ファームウェアのバイナリインターフェース（GATT UUIDおよびパケット構造）は変更せず、既存ファームウェアとの完全な互換性を維持する。
- リファクタリングは段階的（フェーズ制）に進め、常に動作可能な状態を保ちながら移行する。
