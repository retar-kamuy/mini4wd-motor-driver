# Phase 0 調査と設計判断

## 1. 試作の順序

**決定（2026-11-22更新）** — 趣味用の車載ブラシレス基板に直行し、初版車載基板そのものを初回通電と低速評価に使う。別基板の設計・発注・立上げを省き、初版で見つけた性能や収納の問題は改版で扱う。以下の表は比較時の根拠。

| 経路 | 早期に得られる証拠 | 追加の工数・依存条件 |
|---|---|---|
| ブラシ付き実機を流用 | ログ品質、周回とレーン順序、設定適用、接続監視、位置未確定時の挙動 | モーターと車輪の回転計測を追加する場合の搭載工数。003の実機、安全な低速駆動、回転入力の準備が必要 |
| ブラシレスへ直行 | 最終駆動方式の始動、停止、計測のノイズと走行データ | 005の駆動・取付・電源の未解決項目が先に必要。位置推定と駆動の問題の切り分けに工数がかかる |
| ブラシ付き専用PCBを新規製造 | 先行評価で専用車載基板の配置も確認できる | 別の回路設計、業者照合、基板製造、立上げが必要。今回は原則として流用か直行を選ぶ |

同じ意味の目標速度、駆動許可、自然減速、故障、回転数、時刻、データ品質を共通の接続仕様にする。計測・ログ、BLE、学習、区間照合、設定画面、監視と回帰試験を共用する。基板は共通回路を使う一枚構成と制御・駆動を分ける構成を配置で比較する。駆動方式の変更後は、電圧・電流、PWMや転流、減速距離、停止出力、放熱、ノイズ、車輪回転の校正、センサーの姿勢と振動を差分評価する。

根拠は [003の仕様](../003-resolve-pcb-drc/spec.md) と [005の制御器選定](../005-mini4wd-brushless-motor/controller-selection.md)。先行車の合格は最終周回タイムの評価とは別に記録する。

## 2. 車載計測と全レーンの識別

**決定** — 最初は6軸IMUと車輪回転を使う。低速で全レーンを巡回し、開始レーン、旋回・傾斜の特徴、回転数から見積もった距離、レーン遷移を対応付ける。学習とは別の走行で照合し、似た区間の取り違えや未確定区間を記録する。車輪回転は空転やジャンプで誤差を生むため、特徴の並びと推定距離が一致しない場合は位置未確定とする。

**追加センサーの判断** — 区間の取り違えが減らない、または安全に減速を開始できる位置を先に判定できない場合、車載距離センサーやカメラを同じコースで比較する。既存のコース形状を観測し、目印を追加しない。別走行での誤識別、未確定率、判定遅延の改善と、重量・電力・搭載に必要な空間を記録して採否を決める。

## 3. 制御器・駆動・製造

**決定** — BLE、IMU、ログ用メモリー、回転入力、監視と駆動接続を持つ専用制御基板を設計する。小型のBLEモジュールと外付けIMU・Flashを第一の比較案とする。Raytac MDBT50Q-P1MV2とBosch BMI270を比較の起点にし、回転入力、駆動出力、独立停止、拡張の端子収支と、車載時の重量・寸法・調達を照合する。カメラ採用時は画像処理部を分ける構成も比較する。[Raytac製品資料](https://www.raytac.com/product/ins.php?index_id=47)、[Bosch製品資料](https://www.bosch-sensortec.com/en/products/motion-sensors/imus/bmi270)。

006では ROCKET-RC MINI 1525 5500KV を第一評価候補とする。FAULHABER 1218S006Bは005の参照記録に残す。MCT8316ZRは電流・熱の適合を条件に比較する。選定根拠は[駆動性能の机上比較](drive-performance.md)と[電源設計方針](power-architecture.md)に記録する。FGOUTはHall信号に基づくため転流状態と回転の診断に使える。両版共通の走行距離推定には車輪回転入力を使用する。モーター定格、低インダクタンス巻線、始動、連続電流、放熱、ギヤと固定を確認するまで採用は暫定。003の駆動回路を2S電池へ直結しない。[005のモーター設計記録](../005-mini4wd-brushless-motor/documented-motor-design.md)、[TIデータシート](https://www.ti.com/lit/ds/symlink/mct8316z.pdf)。

実装版を決める前に、シャーシ内の収納、端子、電源波形、停止回路と駆動時の負荷を確認する。JLCPCBに正確な型番の調達と実装条件を照会し、ERC/DRC、接続整合、電源・熱・EMC、向きの確認、DFM回答を各段階の記録に残す。現時点で部品の在庫・実装受入や電気的適合は確定していない。

## 4. アプリの役割と走行中の停止

**決定** — 既存のWeb UIとBLEを参照し、最初は対応PCブラウザーで試験する。アプリは停止後のログからマップと初期案を生成し、利用者の確認・調整後に車体へ転送する。初期案は学習走行で観測した速度と区間種別を起点にし、検証した車体ごとの上限内に収める。車体は適用済みの目標と位置推定を使って速度を調整し、アプリ接続と監視応答を確認する。通信が途切れた場合は車体で駆動を遮断し、再接続しても明示的な開始を待つ。[ChromeのWeb Bluetooth資料](https://developer.chrome.com/docs/capabilities/bluetooth)。

走行中にアプリが各区間の駆動指令を都度送る方式も比較した。車体側で照合と駆動制御を行う方針なら、接続要件を維持しつつ、区間内の制御周期に無線往復時間を持ち込まずに済む。減速開始位置から対象区間までの距離、最高試験速度、実測した自然減速・制動距離をもとに遅延予算を定める。通信喪失から実際の遮断までは、検出と停止回路の遅延を含めて測定する。005の暫定監視値は006の保証値に流用しない。
